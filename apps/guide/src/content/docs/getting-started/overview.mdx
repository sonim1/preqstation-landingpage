PreqStation is an execution platform for AI-agent-driven development workflows. It bridges developers and coding agents through a web control plane, the PREQ CLI, optional dispatch integrations, and agent-facing APIs.

If you want the product story before the system diagram, read [Product Philosophy](/guide/getting-started/philosophy/) first.

Read this page when you want to understand how the pieces fit together. If you are trying to get your first runtime connected, use [Quick Start](/guide/getting-started/quick-start/) first and come back here after `status` is readable.

## Recommended First Step

If you're starting PreqStation from scratch, begin with [Quick Start](/guide/getting-started/quick-start/). It starts with `npx -y @sonim1/preqstation@latest install`, then checks local runtime, MCP, and project setup. If you are self-hosting the web app or validating migrations, use [Web App Setup](/guide/web-app/setup/).

## Setup Path Order

- **CLI Default Setup** — [Quick Start](/guide/getting-started/quick-start/) for the fastest CLI installer path
- **Worker-Only Setup** — [Worker Installation](/guide/skill/installation/) when you want manual Claude, Codex, or Gemini worker setup
- **Dispatcher Setup** — add queued delivery only if you need it from the web app: [Telegram Integration](/guide/web-app/telegram/)
- **Web App Setup** — [Web App Setup](/guide/web-app/setup/) for self-hosting, migrations, and first-login details

## Core Systems and Dispatch Paths

PreqStation separates the trigger path from the task engine:

<CardGrid>
	<Card title="PreqStation Web App" icon="setting">
		Task and control plane. It manages tasks, renders the Kanban UI, tracks workflow state and review evidence, exposes REST/MCP-backed APIs, and lets users choose a dispatch target when they want one.
	</Card>
	<Card title="PREQ CLI" icon="rocket">
		User-facing package and command: `@sonim1/preqstation` and `preqstation`. It installs and updates operator-host support, checks `status` and `doctor`, maps projects, and prepares worker runtime support.
	</Card>
	<Card title="Worker Runtimes" icon="approve">
		Claude Code, Codex CLI, and Gemini CLI perform the task work. The task `engine` decides which worker runtime starts, independent of the Hermes/Telegram dispatch path.
	</Card>
	<Card title="Integrations" icon="puzzle">
		Hermes Agent and Telegram are entrypoints for queued or chat-driven delivery. They hand work to the PREQ CLI on an operator host instead of replacing the worker runtime.
	</Card>
	<Card title="MCP" icon="link">
		Agent-facing API bridge. Modern setup normally uses the remote `/mcp` endpoint with browser OAuth. Token/API-key setup remains available for shell-helper mode and older local bridge flows.
	</Card>
</CardGrid>

Some legacy identifiers still mention `preqstation-dispatcher` for compatibility. Treat those as internal compatibility names, not a separate user-facing setup path.

<Aside>
The public canonical repository is `sonim1/preqstation`. The web app source used for local development is still being migrated there, so setup instructions may reference the current development repository until that move is complete.
</Aside>

## Data Flow

The shortest lifecycle is:

```text
create task -> plan task -> implement in worker -> complete to Ready -> verify -> mark Done
```

### Task Creation and Notification

```text
User creates task in the Kanban UI
  -> PreqStation stores it in PostgreSQL
  -> user optionally chooses a dispatch target
  -> PREQ queues Hermes/Telegram relay only when that path is needed
```

### Dispatcher Target vs Engine

- A dispatch target decides how the task is triggered through Hermes or Telegram relay.
- `engine=claude-code | codex | gemini-cli` stays separate from the dispatcher target and decides which local CLI actually runs the task.

### Agent Trigger Paths

```text
Hermes/Telegram path:
  developer chooses a web app dispatch action or hands off through Hermes/Telegram
    -> integration delivers the request to the operator host
    -> PREQ CLI resolves project + task + engine
    -> creates an isolated git worktree
    -> launches the requested coding agent
```

### Agent Execution and Status Reporting

```text
Agent lifecycle:
  inbox -> preq_plan_task -> todo
  todo or hold -> implement -> preq_complete_task -> ready
  ready -> verify -> preq_review_task -> done
  any blocked step -> preq_block_task -> hold
```

## Tech Stack

| Layer      | Technology                                  |
| ---------- | ------------------------------------------- |
| Framework  | Next.js 16 (App Router)                     |
| UI         | React 19, Mantine 8, Tabler Icons, Recharts |
| ORM        | Drizzle ORM                                 |
| Database   | PostgreSQL (Row Level Security)             |
| Validation | Zod                                         |
| Auth       | Session cookies (HMAC-signed), bcryptjs     |

<Aside>
All data is owner-scoped via PostgreSQL Row Level Security. PreqStation is designed for single-developer use.
</Aside>

PreqStation은 하루 종일 컴퓨터 앞에 앉아 있을 수 없는 개발자를 위해 만들어졌습니다. 이제 AI는 거친 구현 초안을 빠르게 만들 수 있습니다. 하지만 실제로 어려운 문제는 작업을 미리 준비하고, 안전하게 dispatch하고, 나중에 돌아왔을 때 정말로 리뷰하고 배포할 수 있는 결과를 받는 일입니다.

## 어디서든 Dispatch

쓸모 있는 작업은 책상 앞에서만 떠오르지 않습니다. 이동 중에도, 미팅 사이에도, 다른 일을 하다가도 나타납니다.

PreqStation은 그 순간 태스크를 잡고 acceptance criteria까지 정리한 뒤, 적절한 때에 실행할 수 있도록 설계되었습니다. 핵심은 계속 키보드 앞에 붙어 있는 것이 아니라, 자리를 비울 때마다 실행 흐름이 끊기지 않게 만드는 것입니다. 미리 준비된 작업은 나중에 Hermes dispatch 경로를 통해 worker에게 전달될 수 있고, 개발자는 돌아와서 결과와 검증 기록을 확인하면 됩니다.

## 1인 개발자와 작은 팀을 위한 도구

대부분의 프로젝트 도구는 더 큰 인간 팀과 더 무거운 프로세스를 전제로 합니다. 그 도구들도 필요할 수 있지만, PreqStation이 풀려는 문제는 그것과 다릅니다.

PreqStation은 이미 실행할 만큼 분명해진 태스크를 다루는 계층입니다. 백로그 계획이나 넓은 협업은 GitHub Issues, Linear, Jira, Notion 같은 기존 도구에 남겨두세요. PreqStation은 범위가 정리된 실행 작업, 리뷰 신호, 그리고 보이는 후속 조치에 집중합니다.

## MVP에서 프로덕션으로

첫 번째 초안 자체는 예전보다 훨씬 싸졌습니다. AI는 MVP 수준의 구현을 빠르게 만들어 줍니다. 여전히 시간을 잡아먹는 부분은 그 초안을 믿고 배포할 수 있는 변경으로 바꾸는 일입니다.

PreqStation은 그 전환에 필요한 가드레일을 더합니다. 격리된 worktree, 명확한 소유권, 리뷰 가능한 노트, 검증 출력, 그리고 터미널 스크롤을 다시 뒤지지 않아도 무슨 일이 있었는지 보여주는 태스크 기록이 그것입니다.

## 엔진과 디스패처를 분리해서 보기

PreqStation에서 engine은 실제로 코드를 실행하는 모델/CLI를 뜻합니다. 예를 들어 `claude-code`, `codex`, `gemini-cli`는 Claude, Codex, Gemini worker 중 무엇을 띄울지 정합니다.

Hermes는 별도의 dispatch 하네스입니다. 태스크를 받아 프로젝트를 찾고, worktree를 만들고, 알맞은 engine을 실행하는 경로를 제공합니다. 즉 Hermes가 태스크를 받았다고 해서 Hermes가 구현 엔진이라는 뜻은 아닙니다. 어떤 채널로 보냈는지와 어떤 모델이 코드를 썼는지를 분리해서 보면 PreqStation의 흐름이 훨씬 단순해집니다.

## 상태와 실행 오버레이

빠르게 이해하기 위한 멘탈 모델은 단순합니다. queued, working, done.

하지만 실제 워크플로우는 더 정확합니다.

- `inbox`: 새로 잡은 작업
- `todo`: 실행 준비가 끝난 작업
- `hold`: 실행이 막힌 작업
- `ready`: 리뷰를 기다리는 작업
- `done`: 검증까지 끝난 작업

`queued`, `working`, `done`은 run-state overlay입니다. 이 값들은 태스크가 지금 dispatch 대기 중인지, worker가 실행 중인지, 실행이 종료되었는지를 보여주지만 workflow status를 대체하지 않습니다. 예를 들어 `todo` 태스크가 `queued`일 수 있고, 같은 `todo` 태스크가 worker에게 claim되면 `working`으로 보일 수 있습니다. 구현이 끝나면 workflow status는 `ready`로 이동해 리뷰를 기다리고, 검증이 끝났을 때 `done`이 됩니다.
